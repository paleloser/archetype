# AGENTS.md

Monorepo with three independently built and deployed apps: `server` (Java/Spring Boot REST API), `webapp` (Next.js
app behind the login), `web` (Next.js/Fumadocs public site: landing page, docs, blog). What the product is, who it is
for and its URLs are in [`PRODUCT.md`](./PRODUCT.md). Each app has its own README with local-dev setup (env vars,
ports, etc.) and its conventions — read the relevant one before working on an app. This file only covers what changes
how you should write and validate code.

## Conversations

Be concise and clear; avoid too many paragraphs in the conversations with the human.
Assume the person you are talking to has enough technical background and context about the project you are working on.
However, if you're implementing a new integration, adopting a new library, or including any other technology not used
already in this project, assume that the human might not be an expert about it.

## Build, test, lint

Run these from the app's own directory unless noted.

```sh
# server (Java 21, Maven)
mvn verify                 # full build: compile, Checkstyle, Spotbugs, unit + integration tests (Docker for Testcontainers)
mvn verify -DskipITs       # skip integration tests
mvn compile                # fast check — Checkstyle already fails the build here, before tests run

# webapp (Next.js/TS)
npm install                # required after any change to server/backend/.../api/v1.yml (see below)
npm run lint
npm run build

# web (Next.js/Fumadocs)
npm run lint
npm run build
```

There are no JS/TS unit test runners configured in `webapp` or `web` — `npm run build` (plus lint) is the validation
bar for those apps. Both pin an exact Node/npm version (`.nvmrc`, `engines`, `engine-strict`): switch to it first.

## Mandatory rules

- **Before touching any file, create and check out a new branch from the trunk** (`develop`, unless `PRODUCT.md` says
  otherwise; e.g. `git checkout -b <short-task-name>`) — never commit directly to the trunk, even for small or
  config-only changes.
- **Commit incrementally as you go**, not as one big commit at the end. Once a logically coherent step is done and
  builds (e.g. a domain-model change, a mapper/API-layer change, a frontend change), commit it before moving to the
  next step. Keep unrelated changes out of the same commit so the branch stays easy to review commit-by-commit.
- **`domain/` in `server` must stay framework-free.** No Spring, JPA, or Jackson imports under
  `<package>.server.domain`. Wiring lives in `boot/configuration/*Configuration.java` (manual `@Bean` methods);
  alternative adapters (PostgreSQL vs in-memory, one email provider vs another, etc.) are selected via
  `@ConditionalOnProperty` in `infra/`, not by editing `boot/`. See `server/README.md` → Layering Rules.
- **Checkstyle and Spotbugs failures are build failures**, not warnings, and run before tests (`process-sources` /
  `prepare-package` phases). Match existing formatting (2-space indent, 140 columns, import order, annotation
  placement) exactly — a non-conforming file fails `mvn compile`, not just `mvn verify`.
- **The REST API is contract-first.** `server/backend/src/main/resources/api/v1.yml` generates the server's
  controllers and DTOs, and `webapp`'s API client (its `postinstall` runs `openapi-generator-cli` into
  `webapp/autogenerated/`). Change the spec first, never hand-write a DTO or a client call. Any change to `v1.yml`
  requires re-running `npm install` in `webapp` before editing code that consumes it, or you'll be coding against a
  stale client.
- **Frontend code style is ESLint-enforced, not Prettier-default**: single quotes, no semicolons, 2-space indent,
  spaced JSX curly braces (e.g. `{ value }`). Do not add semicolons or double quotes — `npm run lint` will fail. This
  applies to MDX in `web` too.
- **Every user-facing string is translated.** `webapp`: colocated `*.i18n.ts` dictionaries. `web`: one MDX file per
  locale, and `i18n/<locale>.json` for the site chrome. Never hardcode copy in one language only.
- **Never commit secrets.** All credentials are read from environment variables with empty defaults in committed
  `application.yml`/`.env.example` files. Don't hardcode a working value anywhere, even temporarily.
- **Open PRs against the trunk, not the release branch.** The trunk is where work lands; the release branch
  (`main`) only tracks released commits.
- **Open PRs as drafts** and mark them ready only after the relevant build command above passes locally. If the
  repository is private, Actions minutes are billed against a finite allowance; the `verify-*` workflows skip draft
  PRs entirely and a new push cancels the run it supersedes. Never mark a PR ready to "see if CI passes" — run the
  build locally first, because that is the same check.
- **When a task is done, push the branch and open the PR** — don't leave finished work sitting as a local, unpushed
  branch.
- **Every commit made by an AI agent must include a `Co-Authored-By:` trailer** identifying the agent (e.g.
  `Co-Authored-By: Claude <noreply@anthropic.com>`), so authorship is traceable in `git log`/`git blame` even though
  the commit is pushed under the operator's own account/credentials.
- **Any agent-authored PR description, PR/issue comment, or review left under a human's account must open with an
  explicit AI-generated notice** (e.g. "🤖 Generated by an AI coding agent on behalf of @<username>") — since the
  GitHub identity alone won't show it wasn't typed by a person, the notice belongs in the content itself.
- **`docker-bake.hcl` is the only place image builds are defined.** Contexts, dockerfiles, tags, cache refs and
  labels for `server`/`web`/`webapp` live there. Adding build arguments or a new image means editing the bake file —
  never inlining the change into a workflow. Verify with `IMAGE_TAG=test docker buildx bake --print`.

## Task triage protocol

Before executing any multi-step or non-trivial request:

1. Briefly evaluate the task complexity (e.g., Simple edit vs. Complex multi-file refactor).
2. Recommend the optimal model to use amongst the ones offered by the current agent.
3. If the currently active model is already optimal, state that and begin.
4. If a different model is recommended, state the recommendation and wait for the user to confirm or switch.

## Recommendations

- Follow the **Object Mother** pattern for server test fixtures (one `FooMother` builder class per entity, under
  `src/test/java`, mirroring the production package) instead of inline test data construction.
- The server has mappers with the same name in different layers (`api/v1/mapper/FooMapper` vs
  `infra/postgresql/mapper/FooMapper`). Double-check the import resolved to the mapper for the layer you're actually
  in.
- Bidirectional `@OneToOne(mappedBy = ...)` relations in `infra/postgresql` require the owning-side back-reference to
  be set explicitly in the `*Mapper`'s `toInfra` method before persisting, or the FK column is saved as `null` and the
  child is silently unreachable on reload.
- Use the terms defined in [`GLOSSARY.md`](./GLOSSARY.md) consistently in code, comments, and API fields. If a task
  references a glossary term with no corresponding class in the code, ask before inventing one — the glossary may be
  ahead of the current implementation.
- Integrations should fail lazily, on first use. If one has to validate eagerly at startup, give it an
  `<slug>.<integration>.enabled` switch so the server still boots without its credentials.
- The agents and skills in [`.claude`](./.claude) learn from you: when you correct one, it records the rule (see
  [`.claude/README.md`](./.claude/README.md#learning)).

## Definition of done

- The relevant build command above passes for every app you touched: `mvn verify` for `server` changes,
  `npm run lint && npm run build` for `webapp` and/or `web` changes.
- If `server/backend/src/main/resources/api/v1.yml` changed, `webapp` was reinstalled and still builds.
- No secrets, credentials, or `.env` values were added to tracked files.
- New/changed server code respects the `domain`/`boot`/`infra`/`api` layering described above.
- New user-facing strings exist in every locale.
- The PR is open as a **draft** against the trunk; it is marked ready only once the checks above pass locally.
- CI/CD changes are validated without spending Actions minutes to find out: `docker buildx bake --print` for anything
  touching `docker-bake.hcl`, `shellcheck` for shell scripts, and `actionlint` (or at minimum a YAML parse) for
  workflow edits. Never "push and see what the runner says".
