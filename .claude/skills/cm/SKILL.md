Run the Community Manager for the product described in `PRODUCT.md`. Arguments: `$ARGUMENTS`.

Read `PRODUCT.md` and this skill's [learnings.md](learnings.md) first. If
[channels.md](channels.md) has no channels, or [editorial-guide.md](editorial-guide.md) still has
`TODO`s in its product sections, follow the Learning protocol in `.claude/README.md` before
drafting anything: ask the maintainer for them in one message and write them in. When the
maintainer edits or rejects a draft, record the reason in `learnings.md` (a rule about voice) or
add the approved post to [examples/](examples/) (a model to imitate).

You are the **orchestrator**, not the Community Manager. The copy, the choice of topics and
the red flags come from the [`community-manager`](../../agents/community-manager.md) agent,
which only knows the product through the public docs and blog. Your job is everything around
it that needs git, GitHub or a browser: gathering candidates, keeping the ledger, running
[`/screenshots`](../screenshots/SKILL.md), and posting. Never rewrite the CM's copy or
overrule its red flags. If you disagree, say so in your reply.

The run has two phases, as in `/pm-scan`. **Phase 1 (Plan)** writes nothing to GitHub. It
gets the drafts, shoots the assets and writes a plan file. **Phase 2 (Apply)** posts the plan,
and only runs when the arguments contain the word `apply`. Forgetting the flag must always be
harmless.

## Modes

- **`scan`** (the default, also when the arguments are only `apply`): the weekly run. Finds
  every candidate the ledger hasn't covered and lets the CM pick at most **3 topics**.
- **`post <topic>`**: on demand. `<topic>` is free text ("the bulk invitations", "remind
  customers they can attach photos"). Exactly one topic, same flow, same ledger.

## Conventions

**Nothing is published to social media.** This skill drafts. The maintainer posts by hand.

**AI notice.** Everything posted to GitHub starts with:
`🤖 Generated by an AI coding agent (CM) on behalf of @<login>`, where `<login>` comes from
`gh api user -q .login`.

**GitHub access.** This skill posts to GitHub Discussions and uploads release assets, which the
REST helper can't do (Discussions are GraphQL-only, uploads go to a different host), so Phase 2
needs the `gh` CLI, authenticated: run it from a workstation, not a cloud session. `<owner>` and
`<repo>` below come from `PRODUCT.md` → Repository → GitHub (or `git remote get-url origin`).

**Label.** `cm/docs-gap`, for a topic the CM couldn't explain from the docs.

**Discussion category.** **CM Drafts** (slug `cm-drafts`). GitHub's API can't create
categories. If it's missing, stop and ask the maintainer to create it (Settings → Discussions,
format "Open-ended discussion").

**Week.** `<ISO year>-W<week>` of today, e.g. `2026-W39`.

**Asset directory.** `.cm/<week>/<topic-slug>/` at the repo root, git-ignored: the run's local
working copy. Nothing in it is ever committed.

**Asset release.** GitHub's API can't attach files to a discussion, so `apply` uploads them to a
**draft** release per week, `cm-assets-<week>` (title `CM assets · <week>`), and the discussion
links them there. A draft creates no git tag, stays out of the release list and triggers no
workflow. **Never publish it.** The discussion never mentions a local path.

## The ledger

The ledger stops topics from being lost or repeated. It isn't tied to a date window. Every
CM Drafts discussion ends with a `## Ledger` section (see
[templates/drafts.md](templates/drafts.md)) with three lists, one change per bullet, each
quoting the change's summary as the release-notes frontmatter had it:

- **Covered**: drafted in this discussion.
- **Queued**: noteworthy, but left out by the cap. Carried forward until drafted.
- **Blocked**: red-flagged, with its `cm/docs-gap` issue. Carried forward until drafted.

The state is:

- **Covered** is the union of the Covered lists of *all* CM Drafts discussions. To get a topic
  drafted again, the maintainer deletes its line from the discussion that covered it.
- **Queued** and **Blocked** are read from the *latest* CM Drafts discussion only. Every run,
  `post` runs included, writes them out again in full, updated.

The release-notes draft entry is rewritten between runs, so its summaries drift. Match
changes against the ledger **on meaning, not wording**, as `/pm-scan` does with issues, and
say why in the plan when a match isn't obvious.

# Phase 1: Plan (no GitHub writes)

Don't run any command that writes to GitHub in this phase: no `gh issue create|edit|comment`,
no `gh label create`, no `gh api` mutation.

## 1. Set up

- Get the login (`gh api user -q .login`), the mode, and the week.
- Check that the `cm-drafts` category exists, and load every CM Drafts discussion with its body:

  ```sh
  gh api graphql -f query='{repository(owner:"<owner>",name:"<repo>"){discussionCategories(first:20){nodes{slug}} discussions(first:50,orderBy:{field:CREATED_AT,direction:DESC}){nodes{number title createdAt body category{slug}}}}}'
  ```

  Keep the `cm-drafts` ones. Build the ledger state as described above. No discussions means
  an empty ledger. That's the first run.
- Load the docs-gap issues: `gh issue list --label cm/docs-gap --state all --json number,title,state,body`.
- Make sure you're on an up-to-date trunk (or a branch of it): the CM works from what the
  trunk has.

## 2. Gather candidates

**`scan`:**

1. Every `changes:` item from the release-notes entries under `web/content/blog/<social locale>/` whose
   frontmatter `date` is within the last 8 weeks, including the current draft entry.
2. Remove the ones already **Covered**.
3. Add every **Queued** item, and every **Blocked** item whose `cm/docs-gap` issue is now
   closed. A Blocked item whose issue is still open stays Blocked, and isn't sent to the CM.
4. For each candidate, note whether it's **live**, meaning its entry is on the release branch:
   `git cat-file -e origin/<release branch>:web/content/blog/<social locale>/<slug>.mdx`. The current draft entry never is.

If nothing is left, don't call the agent. Go to step 5 with an empty run.

**`post <topic>`:** the topic as given is the only candidate. Also pass any release-notes
changes that seem to match it, with their live status, so the CM can link the right entry.

## 3. Ask the Community Manager

Spawn the `community-manager` agent (Agent tool, `subagent_type: community-manager`). It
starts cold, so give it everything it needs in the prompt:

- The mode, and the cap: at most 3 topics for `scan`, the one topic for `post`.
- The candidates, each with its summary, `type`, blog entry slug and live status. Queued
  ones are marked as such: they go first unless the CM finds them no longer noteworthy.
- The path to [editorial-guide.md](editorial-guide.md), the standard every post is held to,
  to [channels.md](channels.md), for it to read, and to [examples/](examples/): posts the
  maintainer wrote or approved, which it reads for voice.
- The output format below, verbatim.

````
For each candidate, one block:

### <change summary, verbatim>
- Decision: draft | skip | queue | red flag
- Why: <one line>

For a "red flag", also:
- Question it fails: what is it | who is it for | how do I use it
- Docs passage: <quote and page path, or "none found">
- What a customer is left wondering: <plain words>

For a "draft", also:
- Topic: <short title, in the social media locale>   Slug: <kebab-case>
- Audience: <one or more of PRODUCT.md's audiences>
- Central idea: <one sentence: the problem, who has it, and what changes for them>
- Link: <public site URL of the docs page or blog entry>
- Asset: existing <path under web/public/…> | new video | new still | none
- Asset brief (only when new): <what to show, where the reader finds it in the app, in their words>
- Not live yet: yes | no
Then one "#### <channel>" section per channel in channels.md, holding the post exactly as it
should be pasted.

Merge candidates that are really one topic into one block and list the merged summaries
under it. Draft at most <cap> topics, and mark the other noteworthy ones "queue".
````

Check the reply against the format. If a block is missing something, ask the same agent to
complete it (SendMessage). Don't fill it in yourself.

Then **fact-check every claim in the posts against the docs page it cites** (the CM links it).
Copywriting pulls toward claims that sound right but aren't there, e.g. "the user is
notified when you attach a photo". Send each unsupported line back to the same agent with the
docs passage that contradicts it or the note that none supports it, and use its rewrite. The
CM owns the copy: never fix it yourself.

Review it the same way against [editorial-guide.md](editorial-guide.md). A post fails when it
opens by explaining what the product is, puts the mechanism before the benefit, mixes the
audiences' benefits, uses the guide's corporate words, or ends without one clear action. Send
each failure back to the agent with the guide's rule, and use its rewrite.

## 4. Assets

Create `.cm/<week>/<topic-slug>/` for each drafted topic.

- **Existing asset:** copy it in. For themed stills (`-light` / `-dark`), take the light one.
- **New assets:** run [`/screenshots`](../screenshots/SKILL.md) once, with **one brief for all
  the topics that need one**. This step is part of the run, not an offer to make afterwards.
  The brief pins everything `/screenshots` would otherwise ask about:

  > Social media assets, destination **outside the repo** (commit nothing). Locale `<social locale>`,
  > **dark theme**. For each subject, record a **video in two cuts** at the social video
  > viewports: vertical 9:16 (608 × 1080) for Instagram Reels, and horizontal 16:9
  > (1920 × 1080) for LinkedIn. Under 30 s each, **no on-screen text**: no captions, no
  > chapter cards, no overlays. Subjects: (1) `<CM's asset brief>` — audience `<…>`;
  > (2) … For a "new still" subject, one 16:9 still instead.

  If `/screenshots` stops on a missing prerequisite (no seeds, no login), the topic keeps its
  draft with no asset, and the plan says so.
- **Convert** each kept recording to MP4, since Instagram and LinkedIn don't accept `.webm`,
  into the topic's directory, cropped to the viewport (in case the recording was padded) and
  scaled to the network's size:

  ```sh
  # 9:16, from the 608 × 1080 viewport
  ffmpeg -loglevel error -i <in>.webm -vf "crop=608:1080:0:0,scale=1080:1920:flags=lanczos" \
    -c:v libx264 -crf 18 -pix_fmt yuv420p -movflags +faststart -an <topic-slug>-9x16.mp4
  # 16:9, from the 1920 × 1080 viewport (already full size)
  ffmpeg -loglevel error -i <in>.webm -vf "crop=1920:1080:0:0" \
    -c:v libx264 -crf 18 -pix_fmt yuv420p -movflags +faststart -an <topic-slug>-16x9.mp4
  ```

  Look at a frame of each before keeping it.

  If `ffmpeg` is missing, leave the `.webm` there and say so.

Also drop each channel's post text into the topic's directory as `<channel>.txt`, so it can be
copied from there too.

## 5. Plan the GitHub changes

- **Red flags.** For each one, look for an open `cm/docs-gap` issue about the same gap (on
  meaning). If there's a match, plan a comment only when this run adds something new. If not,
  plan a new issue from [templates/docs-gap.md](templates/docs-gap.md), titled
  `🚩 Docs gap: <what a customer can't figure out>`, labelled `cm/docs-gap`. Number new ones
  `#new-1`, `#new-2`…
- **The discussion.** Write it from [templates/drafts.md](templates/drafts.md), titled
  `CM Drafts · <week>` for `scan` or `CM Post · <topic> (<YYYY-MM-DD>)` for `post`. The ledger:
  - Covered: every change merged into a drafted topic.
  - Queued: the previous Queued items that weren't drafted, plus this run's "queue" decisions.
    Drop items the CM marked "skip".
  - Blocked: the previous Blocked items that weren't drafted, plus this run's red flags, each
    with its issue.

  An empty `scan` still gets a discussion ("Nothing worth posting this week"), because it
  carries the ledger forward. Never pad it with topics.

## 6. Write the plan file

Each run writes **its own plan file**, so a `post` run never overwrites a scan that hasn't
been applied yet: `/tmp/cm/plan-scan-<week>.md` for `scan`, `/tmp/cm/plan-post-<topic-slug>.md`
for `post` (the slug the CM gave the topic). Write it with, in this order: `## New issues` (placeholder id, title, labels,
full body), `## Comments` (issue and full body), `## Discussion` (title and full body), and
`## Assets` (each file to upload, with its local path). In the discussion body, each asset is
a link placeholder, `{{asset:<file name>}}`, which `apply` fills in after uploading.

Then check the arguments: `$ARGUMENTS`. If they don't contain the word `apply`, **stop here**.
Reply with the plan file and the words "Plan only: nothing was written to GitHub. Run
`/cm <same mode> apply` to post it."

**A later `apply` reuses an existing plan** instead of drafting and shooting again: for `scan`,
this week's `plan-scan-<week>.md`; for `post <topic>`, the `plan-post-*.md` whose discussion
title matches the topic (ask if more than one could). Warn if it's more than a few days old,
since the drafts may be stale. With no matching plan, run Phase 1 first.

**Order matters for the ledger.** Queued and Blocked come from the latest discussion, so if
both a scan plan and a post plan are pending, apply the scan first.

# Phase 2: Apply (only with `apply`)

Carry out the run's plan file exactly as written, without re-deciding anything.

1. Make sure the label exists:

   ```sh
   gh label create cm/docs-gap --color fbca04 --description "Something the CM agent couldn't explain from the docs" 2>/dev/null || true
   ```

2. Create the new issues and note the real number for each `new-<k>`. Post the comments.
3. Upload the assets to the week's draft release, creating it if it doesn't exist, and note each
   file's download URL:

   ```sh
   gh release view cm-assets-<week> >/dev/null 2>&1 || gh release create cm-assets-<week> --draft \
     --title "CM assets · <week>" --notes "<AI notice> Social media assets for the CM Drafts discussions of <week>. A draft on purpose: never publish it."
   gh release upload cm-assets-<week> <files…> --clobber
   gh release view cm-assets-<week> --json assets --jq '.assets[] | [.name, .url] | @tsv'
   ```

4. Replace every `#new-<k>` in the discussion with its real number, and every
   `{{asset:<file name>}}` with a markdown link to its URL. Check the body has no local path
   left, then post it to **CM Drafts**:

   ```sh
   gh api graphql -f query='{repository(owner:"<owner>",name:"<repo>"){id discussionCategories(first:20){nodes{id slug}}}}'
   gh api graphql -f query='mutation($repo:ID!,$cat:ID!,$title:String!,$body:String!){createDiscussion(input:{repositoryId:$repo,categoryId:$cat,title:$title,body:$body}){discussion{url}}}' \
     -f repo="<repository id>" -f cat="<cm-drafts category id>" -f title="…" -f body="…"
   ```

5. Reply with the discussion URL, the issue URLs, the release, and anything that failed.
