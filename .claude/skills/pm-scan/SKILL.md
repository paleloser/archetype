Run the weekly product scan for the product described in `PRODUCT.md`. Arguments: `$ARGUMENTS`.

The scan has two phases. **Phase 1 (Plan)** is read-only: it works out every GitHub
change and the digest, and writes them to a plan file. **Phase 2 (Apply)** carries out
the plan, and only runs when the arguments contain the word `apply`. Without `apply`
the scan ends after Phase 1. Forgetting the flag must always be harmless.

## Conventions

**Labels.** `pm/idea`, `pm/risk`, `pm/hot`, `pm/stale`, `pm/digest`, plus
`Prio/Low`, `Prio/Medium`, `Prio/High` (created in Phase 2 if missing). Never add `enhancement`. The maintainer adds it
when accepting an idea. `pm/digest` issues never get a `Prio/*` label.

**GitHub access.** Use GitHub's REST API only, through
[scripts/gh-rest.sh](scripts/gh-rest.sh) (plain `curl` + `jq`). Don't use the `gh` CLI:
it isn't installed in Claude Code cloud sessions, and its higher-level subcommands go
through GraphQL, which those sessions can't reach. In particular, never use
`gh auth status` to check whether GitHub access works — it validates the token over
GraphQL too, so in a cloud session it reports the token as invalid even when it works
fine over REST. To check access (e.g. before deciding whether to run with `apply`), use
`$GH GET user` — the same call step 1 already makes to get the login — and treat a
non-2xx or missing `.login` as the real "not authenticated" signal, not `gh auth
status`'s verdict. This file calls the helper as `$GH`:

```sh
GH=.claude/skills/pm-scan/scripts/gh-rest.sh   # from the repo root
$GH GET    <path>              # one page
$GH GETALL <path>              # every page, merged into one JSON array
$GH POST|PATCH <path> <file>   # <file> holds the JSON request body
$GH DELETE <path>
```

Shell state doesn't persist between Bash calls, so set `GH=` and `REPO=` in every call that uses
them. `REPO` is `PRODUCT.md` → Repository → GitHub, or, while that is `TODO`:

```sh
REPO=$(git remote get-url origin | sed -E 's#^.*github\.com[:/]##; s#\.git$##')
```

Pipe the output through `jq` to pick fields. The helper sends `GITHUB_TOKEN`/`GH_TOKEN`
when set; in cloud sessions the proxy supplies the credentials. GitHub Discussions are
GraphQL-only, so they're out of reach: the PM Digest is posted as an issue, not a
Discussion.

**AI notice.** Everything posted to GitHub (issue bodies, comments, digests) starts
with: `🤖 Generated by an AI coding agent (PM) on behalf of @<login>`, where `<login>`
comes from `$GH GET user | jq -r .login`.

**Reference.** One piece of evidence from one source. Always a single bullet in this
exact format, wherever it appears (issue bodies, comments, digest):

```
- <YYYY-MM-DD> · **<Source name>** (<type>[, <engagement>]) · [<title>](<url>)[ @ <mm:ss>] — <what it says, one line>
```

- `<YYYY-MM-DD>` is the item's publication date, not the scan date.
- `<type>` is one of `article`, `video`, `community`, `changelog`, `product page`, `release notes`.
- `<engagement>`, when the source exposes it: views, upvotes or comments, followed by
  the multiplier against the source's recent average, e.g. `180k views, 3×`. Omit it
  when unknown. Never estimate it.
- `@ <mm:ss>` is only for videos, pointing to where the point is made. Omit it if you
  only had metadata.
- Videos read from metadata only (no transcript) end with ` *(metadata only)*`.
- Non-English sources: the summary is in English, the title stays as published.
- **No duplicates.** A reference whose URL already appears on an issue (body or
  comments) is never added to it again.

# Phase 1: Plan (read-only)

In this phase you must not run any command that writes to GitHub: no issue creation,
edit or comment, no label create/add/remove, no `$GH` call other than `GET`/`GETALL`.
Only reads.

## 1. Set up

Get the login with `$GH GET user | jq -r .login`, and create the working directory with
`mkdir -p /tmp/pm-scan`.

**Scan window.** It always ends today. For the start:

- If the arguments contain `since=<YYYY-MM-DD>`, use that date. This is for tests and
  backfills.
- Otherwise, find the latest PM Digest issue and use the day after its window's end
  (the second date in its title). If there is none, use the last 7 days.

An **empty window** (the start is after today) doesn't end the scan. Skip the
non-provider sources, but still run the provider-risk exception in step 3, and steps
4–8.

```sh
$GH GET "repos/$REPO/issues?state=all&labels=pm/digest&sort=created&direction=desc&per_page=1" \
  | jq -r '.[0].title // "none"'
```

## 2. Ground yourself

Read `PRODUCT.md`, this skill's [learnings.md](learnings.md), `GLOSSARY.md`, `README.md`,
`architecture/` (if any) and skim `web/content/docs/` in the agents' working language.

**Learning.** If [sources.md](sources.md) has no sources yet (only `TODO`s), or `PRODUCT.md` has
no Integrations, Competitors or Principles, follow the Learning protocol in
`.claude/README.md` before reading anything: propose candidates (the integrations and
competitors you can find in the repository and on the web, the industry's trade press,
communities and YouTube channels), ask the maintainer to confirm or correct them in one
message, and write the answers to `sources.md` and `PRODUCT.md`. When the maintainer later
corrects a run ("that source is noise", "never file ideas about X"), record it in
`learnings.md`. Then load
the backlog, including your own earlier work, with full bodies:

```sh
$GH GETALL "repos/$REPO/issues?state=all" \
  | jq -c '.[] | select(.pull_request == null) | {number,title,state,labels:[.labels[].name],body}' \
  | head -n 300
```

For issues a finding might match, also read their comments to check for references
that are already there:

```sh
$GH GETALL "repos/$REPO/issues/<n>/comments" | jq -r '.[].body'
```

## 3. Read the sources

Go through [sources.md](sources.md) and collect every item published inside the scan
window.

**Exception for provider sources:** an announced change whose effective date is still
in the future is in scope whatever its publication date. The URL-dedup rule and the
backlog matching in step 4 make sure it's only filed once.

- **Feeds and pages**: WebFetch. If a source fails, is blocked or paywalled, note it for
  Run health and move on. Never guess its content.
- **YouTube**: the channel RSS lists titles, dates, descriptions and
  `<media:statistics views=…>`. The engagement baseline is the average views of the
  other videos in the same feed. For a video that looks relevant, try the transcript:

  ```sh
  command -v yt-dlp >/dev/null || pip install -q yt-dlp
  yt-dlp --skip-download --write-auto-subs --sub-langs "en.*,es.*" --sub-format vtt -o "/tmp/pm-scan/subs/%(id)s" "<video url>"
  ```

  If that fails (YouTube often blocks cloud servers), fall back to the title and
  description, and mark the reference *(metadata only)*.
- Use WebSearch only to confirm or clarify a finding from a listed source, never to
  find new ones.

## 4. Classify each finding

Apply your role's judgment. Drop anything irrelevant, and drop anything that breaks a
Principle in `PRODUCT.md` and can't be reworked into a version that passes it. For the
rest, decide what it is:

- **Provider risk**: a change at a provider that could break or constrain the product.
- **Idea**: a concrete change the product could make.
- **Market insight**: a relevant trend that isn't a concrete change yet.

For ideas and risks, look for an existing issue that covers the same thing. Match on
meaning, not wording, and include issues that aren't the PM's (e.g. a `bug` filed by
the maintainer). Record why each match is a match: the digest shows it, so the
maintainer can catch wrong merges.

## 5. Plan issue changes

**Provider risk.**
- New: plan an issue from [templates/risk.md](templates/risk.md), labels `pm/risk` +
  `Prio/High`. Title: `🚨 <what changes>`.
- Existing and open: plan a comment with the new reference(s), plus a body update if
  the deadline or impact changed.
- The idea lifecycle below doesn't apply to risks.

**New idea.** Plan an issue from [templates/idea.md](templates/idea.md), labels
`pm/idea` + `Prio/Low`. Title: `💡 <what the product would do>`, in glossary terms.

**Existing idea**, i.e. an open issue labelled `pm/idea`: plan appending the new
reference bullets to its `## References` list, and one comment with the same bullets so
the maintainer gets notified.

**Match with another issue.** A finding can match an issue without `pm/idea`: an
accepted idea, or a backlog item that isn't the PM's. If it's open, plan a comment with
the new references and change nothing else. If it's closed, don't touch it and mention
it in the digest.

If the references for a match are all already on the issue, plan nothing for it.

## 6. Recompute every open `pm/idea` issue

This includes ideas that got nothing new this run. Treat planned new references as
already added. Everything is derived from the `## References` list, so the result is the
same however many times it's run.

1. **Base priority from distinct sources** (all time): 1 → `Prio/Low`,
   2–3 → `Prio/Medium`, 4+ → `Prio/High`.
2. **Hot.** The idea is hot if any of these holds over references dated in the last
   14 days:
   - Breadth: ≥3 distinct sources.
   - Engagement: a reference with a multiplier ≥2×.
   - Momentum: more references in the last 14 days than in the 28 days before them.

   If hot: `pm/hot`, and priority one level up (capped at `Prio/High`). If not: no
   `pm/hot`.
3. **Stale.** `pm/stale` if the newest reference is older than 6 weeks, otherwise not.
   A stale idea keeps its priority. The maintainer decides whether to close it.
4. Exactly one `Prio/*` label. Plan only the label changes that differ from the
   current labels, and remember each one for the digest.

## 7. Write the digest

Write it from [templates/digest.md](templates/digest.md), titled
`PM Digest · <ISO year>-W<week> (<Mon d>–<Mon d>)` for the scan window. For an empty
window, use today's week and today's date for both ends. Every section is
always present. When a section has nothing, write `Nothing this week.` Never drop it.
The digest describes the plan as if it had been applied, with issue numbers written
as `#new-1`, `#new-2`... for issues not created yet.

The digest is posted as an issue labelled `pm/digest` only (no `pm/idea`/`pm/risk`,
no `Prio/*`), never a Discussion — see **GitHub access** above.

## 8. Write the plan file

Write `/tmp/pm-scan/plan.md` with these sections, in this order, each item complete
enough to apply without re-deciding anything:

1. `## Labels`: label changes per issue (`#<n>: +pm/hot, -Prio/Low, +Prio/Medium`).
2. `## New issues`: per issue, a placeholder id (`new-1`...), title, labels, full body.
3. `## Body updates`: per issue, the full new body.
4. `## Comments`: per issue, the full comment body.
5. `## Digest`: title, the `pm/digest` label, and full body.

Then check the arguments: `$ARGUMENTS`. If they don't contain the word `apply`, **stop
here**. Reply with the full plan file and the words "Plan only: nothing was written to
GitHub. Run `/pm-scan apply` to carry it out."

# Phase 2: Apply (only with `apply`)

Carry out `/tmp/pm-scan/plan.md` exactly as written, without re-deciding anything.
Every step below is a REST call through `$GH`, per **GitHub access** above. Build each
request body as a JSON file under `/tmp/pm-scan/` with `jq` (e.g. `new-1.json`,
`comment-<n>.json`), reading the Markdown from its own file with `--rawfile`. Plan
Markdown isn't safe to put on the command line or to hand-escape into JSON.

1. Make sure the labels exist. Creating one that already exists fails with 422, which
   is fine:

   ```sh
   for l in "pm/idea:1d76db:Idea proposed by the PM agent" "pm/risk:d93f0b:Provider risk found by the PM agent" \
            "pm/hot:ff7b00:PM idea with hot signals in the last 14 days" "pm/stale:cccccc:PM idea with no new references in 6 weeks" \
            "pm/digest:0e8a16:Weekly PM digest issue" "Prio/Low:c2e0c6:Low priority" \
            "Prio/Medium:fbca04:Medium priority" "Prio/High:d93f0b:High priority"; do
     IFS=: read -r n c d <<<"$l"
     jq -n --arg name "$n" --arg color "$c" --arg description "$d" '{name:$name,color:$color,description:$description}' \
       > /tmp/pm-scan/label.json
     $GH POST repos/$REPO/labels /tmp/pm-scan/label.json >/dev/null 2>&1 || true
   done
   ```

2. Create the new issues and note the real number for each `new-<k>`:

   ```sh
   jq -n --arg title "<title>" --rawfile body /tmp/pm-scan/body-new-1.md \
     '{title:$title, body:$body, labels:["pm/idea","Prio/Low"]}' > /tmp/pm-scan/new-1.json
   $GH POST repos/$REPO/issues /tmp/pm-scan/new-1.json | jq .number
   ```

3. Apply body updates, comments and label changes:

   ```sh
   # Body update
   jq -n --rawfile body /tmp/pm-scan/body-<n>.md '{body:$body}' > /tmp/pm-scan/body-<n>.json
   $GH PATCH repos/$REPO/issues/<n> /tmp/pm-scan/body-<n>.json >/dev/null

   # Comment
   jq -n --rawfile body /tmp/pm-scan/comment-<n>.md '{body:$body}' > /tmp/pm-scan/comment-<n>.json
   $GH POST repos/$REPO/issues/<n>/comments /tmp/pm-scan/comment-<n>.json >/dev/null

   # Add labels (one call, every +label from the plan line together)
   jq -n '{labels:["pm/hot","Prio/Medium"]}' > /tmp/pm-scan/labels-<n>.json
   $GH POST repos/$REPO/issues/<n>/labels /tmp/pm-scan/labels-<n>.json >/dev/null

   # Remove a label (one call per -label; a "/" in the label name must be percent-
   # encoded as %2F, e.g. Prio/Low -> Prio%2FLow, or the REST call targets the wrong path)
   $GH DELETE "repos/$REPO/issues/<n>/labels/Prio%2FLow" >/dev/null
   ```

4. Create the digest the same way as step 2 — an issue labelled only `pm/digest` (no
   `Prio/*`, no `pm/idea`/`pm/risk`) — after first replacing every `#new-<k>` in its
   body with the real issue number created in step 2.
5. Reply with the digest issue's URL, and anything that failed to apply. `$GH` exits
   non-zero and prints GitHub's error body when a call fails.
